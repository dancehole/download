# 需求与方案：相册 / 共享文件的「删除」与「过期」（2026-09-16）

## 一、需求原文

> 检查 download 项目里，相册和共享文件，删除是否能正确删除本地文件 + OSS 文件 + 其他东西，
> 完全释放内存。如果是过期，则只屏蔽链接，不删除本地文件（我发现文件的删除好像有问题）

拆成三条可验收的规则：

| # | 规则 | 说明 |
|---|------|------|
| R1 | **手动删除 = 清干净** | 相册「删除整个相册」/ 共享文件「删除」后，本地文件、OSS 对象、数据库记录（含级联的 photo、album_admin_acl）全部消失，不留孤儿 |
| R2 | **过期 = 只屏蔽链接** | 到达 `expires_at` 后链接失效（分享页 + 原图/预览/RAF/下载全部拒绝），**本地文件与 OSS 对象原样保留**，管理员可续期或手动清理 |
| R3 | **清理动作要可观测** | 删除过程中任何一端（本地 / OSS）没删掉，必须如实上报，不能静默 `pass` 导致空间悄悄泄漏 |

## 三、问题清单与成因

1. **过期相册完全不设防**（P0）：`routers/share.py` 只看 `local_cleared_at`，从不看 `expires_at`，
   到期后分享链接仍然可用。前端的注释也写着「仅过期的相册仍可正常浏览」——按新需求必须改成拦截。
2. **过期共享文件的分享页仍可打开**（P1）：`GET /share/files/{token}` 没有过期判断，只有下载端点判断。
3. **路径失效时删不干净**（P0，就是用户看到的「删除有问题」）：`_local_candidates`
   之前不存在——删除只试 `storage_path`；项目目录从 `activity-image-list` 改名成 `download` 后，
   老记录的绝对路径失效，于是「记录删了、文件留在 `storage/FILES_DIR/{file_id}`」→ 153MB 孤儿由此产生。
   下载端点本来有兜底逻辑，删除没有 → 两边行为不一致。
4. **静默失败**（P1）：共享文件删除时 OSS 异常被 `except: pass`；相册删除时 `clear_oss` 返回 -1
   也被忽略 → 数据库记录一删，OSS 对象永久失去索引，空间无法回收。
5. **清空 OSS 被误当成「相册已清理」**（P1，UI）：`purged = local_cleared OR oss_cleared OR purged_at`，
   后台用它把过期时间下拉框禁用、把卡片标成红色「已清理 · 照片已删除」。所以 KX7BUB4P 今天
   点了「清空 OSS」后，**过期时间不能再改**了（照片其实好好的）。照片上传区只按 `local_cleared` 隐藏，逻辑不一致。
6. **清空 OSS 在 OSS 关闭时会把引用抹掉**（P2）：`clear-oss` 端点在 OSS 未启用时仍会执行
   `clear_event_oss_keys`（把 `photo.oss_*` 置 NULL）+ 打标记，桶里的对象从此找不到引用。
7. **死代码**（P2）：`models.list_expired_share_files` / `mark_share_file_purged`（过期自动清理的遗留）
   已无调用方，且与「过期不删文件」的新策略冲突，容易误用。

## 四、本次改动

### 后端

| 文件 | 改动 |
|------|------|
| `app/routers/share.py` | 新增 `_block_reason(ev)`：`local_cleared_at` → 空壳提示；`expires_at <= now` → 「相册分享链接已过期」；5 个分享端点（info/photos/preview/original/raf）统一 `fail(410, …)`。**只拦截，不碰文件** |
| `app/routers/files.py` | 新增 `_local_candidates()`（`storage_path` + `FILES_DIR/{file_id}` 兜底）与 `_is_expired()`；删除改为逐个候选路径删除并如实上报；OSS key 存在即尝试删除，失败/未启用写入 `oss_error`；`share_file_info` 与 `download` 统一 410 拦截；下载复用同一套路径解析 |
| `app/cleanup_service.py` | 删除顺序固定为 **OSS → 本地 → 数据库**；OSS 删除失败则中止（不删数据库记录），返回 `success=False` + 原因；`rmtree` 后若目录仍在会告警；`clear_oss` 未启用时明确记日志 |
| `app/routers/events.py` | `clear-oss`：若相册仍有 OSS 引用但 OSS 未启用 → `fail(503)` 中止（不抹掉引用）；`DELETE /events/{id}`：`success=False` → `fail(502, 原因)` |
| `app/models.py` | 新增 `count_event_oss_photos()`；删除无调用的 `list_expired_share_files` / `mark_share_file_purged`（保留 `purged_at` 列以兼容历史数据） |

### 前端

| 文件 | 改动 |
|------|------|
| `js/admin.js` | 卡片/详情状态改用 `local_cleared` 判定「已清理」（红），`oss_cleared` 单独显示灰色「OSS 已清空」；过期时间下拉框的 `disabled` 改按 `local_cleared` → 清空 OSS 后仍可改过期时间；共享文件删除返回 `success=false` 时弹出「仍有文件未清干净」的告警 |
| `file.html` | 失效卡片显示后端返回的具体原因（如「链接已过期」）；「已清理」文案不再写「自动删除」；内联 i18n/api 版本号 +1 |
| `js/gallery.js` | 注释与新行为对齐（过期 = 拦截链接） |
| `js/i18n.js`、`admin.html`、`gallery.html` | 新增 `delete_file_partial`、`cleaned_oss_chip` 文案；静态资源 `?v=` 版本号 +1 以确保浏览器不拿旧脚本 |

## 五、待确认 / 未执行事项

1. **需要重启服务**（`systemctl restart download`）本次改动才生效——等你确认后再执行。
2. **磁盘上的历史孤儿**（153MB + 25B + 7MB + 56KB，共约 160MB）是否清理？
   清理脚本会先打印清单、逐个 `os.remove`，不动任何数据库记录。
3. **即将到期的两个相册**：9EPBPDN8 与 KX7BUB4P 都是 **2026-09-19** 到期，
   改动上线后链接会自动失效（本地文件保留）。是否需要顺延过期时间？
4. **共享文件过期后的分享页形态**：本次统一为「链接失效」（显示后端给的过期原因），
   与相册一致。若你更想保留「显示文件名+大小、但禁用下载按钮」的老形态，改一行即可。
5. 建议为 `share_file.storage_path` 增加启动时自愈（发现路径不存在就改成 `FILES_DIR/{file_id}`），
   避免再次出现「记录里路径失效」的情况——需要你确认是否要加。
